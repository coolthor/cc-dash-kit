# Assemble a personal dashboard

When the user asks to customize the installed dashboard, follow these steps. Keep the installed plugin from GitHub and write its local `dash.config.json`; do not replace the marketplace source with a local checkout.

Match the language of the user's latest conversation, regardless of the language of this guide or the project's `CLAUDE.md`. A Chinese request means all three questions and setup replies must be in Traditional Chinese; an English request means English.

1. **Detect locally.** Run `which nvidia-smi` and `df -h /`. Probe only `localhost` or `127.0.0.1` on ports 11434 (Ollama), 1234 (LM Studio), 8000 and 8080 with a three second timeout. A response means the service may be useful; ask before adding it. Keep the exact URL that returned a successful HTTP status. Do not invent a service API path such as `/api/tags` or `/v1/models` from the port number. Do not scan a subnet or probe another host during detection.
2. **Ask exactly three questions in the user's conversation language, one at a time, and wait for each answer.** Use plain text questions so a terminal or Desktop user can answer directly: (a) What do you repeatedly check while working? (b) Do you delegate work to other AI systems? If yes, offer `pause-flag` and its read only `pause_status` tool, and tell the user to ask Claude to call it before dispatching. (c) Which machines or endpoints should appear, if any? Ask for display name and URL, never credentials. Treat an unanswered question as unanswered; ask it again before writing config.
3. **Choose from `src/sources/` first.** Default `quota` and `session` already work without configuration. Available opt ins are `gpu`, `disk`, `http-probe`, and `pause-flag`. Add a source file only when the library cannot express the request. Follow `{ id, detect($), sample($), card(data) }`; the `$` passed to sources is the scoped API adapter in `hooks/register.tsx`. Give every new source a parse test and a bounded sample. If detection fails, omit that card. A sample error stays on its own card.
4. **Write `dash.config.json`.** Use `dash.config.example.json` as a shape guide; use no keys, tokens, or passwords. If the user’s conversation language differs from automatic detection, set `locale` to `en` or `zh-TW`. `cards` is an ordered list. `path` must be absolute. `http-probe` needs one HTTP(S) `url` or an `endpoints` array of `{ name, url }` objects. Verify every configured endpoint returns a successful status; fix a 4xx/5xx URL before presenting the dashboard. `pause-flag` needs an absolute path in an existing writable directory. Make the smallest useful version first. Run `claude plugin validate .` until it passes, then `claude plugin test .` and the parse/config tests. Ask the user to run `/cc-dash` after writing config so the pane reloads it immediately. Show the assembled dashboard to the user, then refine it from their criticism.
5. **Respect boundaries.** Never read conversation logs, transcripts, or history to infer preferences. Never write tokens or credentials to configuration. Never perform network scans in a hook. The pause query is advice for Claude, not a permission boundary. The button is the only UI control for the configured flag; it does not control external dispatch clients by itself.

The command `/cc-dash` opens the pane. In a terminal, `/tui fullscreen` is needed for a docked sidebar; ask consent before changing the saved layout.
